= Known limitations
:description: Understand the known limitations of the system, including design decisions and constraints from upstream components
:revdate: 2026-09-21
:page-revdate: {revdate}

This document tracks the current, known limitations of {rte-name}. Some
are explicit design decisions, some are constraints inherited from upstream
components (kernel/eBPF, Kubernetes, container runtimes). The goal is to help
you understand the limitations and make informed decisions about your
{rte-short-name} deployment.

[#_privileged-containers-can-run-code-outside-their-allow-list]
== Privileged containers can run code outside their allow-list

{rte-short-name} enforces a per-container executable allow-list against processes
running on the container's *own* root filesystem, and it trusts the pod spec as
input (host volumes, mount propagation, and OCI mounts are assumed intentional).
A privileged container (for example with `CAP_SYS_ADMIN` / `CAP_SYS_CHROOT`, or
`hostPID`) can cross filesystem and mount-namespace boundaries. {rte-short-name}
pins exec-path resolution to the container's registered root filesystem, so the
following boundary crossings are detected and denied in protect mode:

* executing a file on a *foreign* root filesystem reached through a procfs magic
  link (for example `/proc/1/root/<allowed-path>` or another process's
  `.../root`, `.../exe`, `.../fd/N`), and
* `chroot` into a sub-directory of the container's own root filesystem to make an
  attacker-controlled file resolve to an allow-listed path.

The remaining boundary crossings below are intentionally left to other layers.

=== Opting a container out: `allowForeignRootExec`

Foreign-root execs are denied by default. Some privileged containers legitimately
need to run binaries from the host or another root filesystem (for example node
agents that exec host tools via `/proc/1/root/...`). For those, set
`allowForeignRootExec: true` on the container's rules:

[source,yaml]
----
spec:
  mode: protect
  rulesByContainer:
    my-privileged-container:
      allowForeignRootExec: true
      executables:
        allowed:
          - /entrypoint
----

* *Impact*: this is a per-container opt-out that applies only to the container it
  is set on. When enabled, foreign-root execs for that container are permitted
  *unconditionally* — the executable allow-list is bypassed for files that
  resolve to a foreign root filesystem. Enable it only for trusted, privileged
  workloads that must run host/foreign binaries.

=== Why mount-based bypasses are not handled here

A process with `CAP_SYS_ADMIN` can `mount --bind` (or overlay/tmpfs) an
attacker-controlled file over an allow-listed path, and `pivot_root` into a
crafted root (which itself requires a mount). Blocking these belongs at the
syscall layer.

* *Impact*: if a privileged container can call `mount`/`move_mount`/`pivot_root`,
  it can replace the content behind an allow-listed path. Restrict these syscalls
  with a *seccomp* profile (or avoid granting `CAP_SYS_ADMIN`). Reimplementing
  mount gating in eBPF would be partial and racy, so it is out of scope.

=== Why interpreter and loader abuse is not handled here

If you allow-list an interpreter or dynamic loader (for example `bash`, `sh`,
`python`, or `ld.so`), it can execute arbitrary scripts or code that the
executable allow-list cannot observe.

* *Impact*: allow-listing an interpreter effectively allows anything it can run.
  This is inherent to allow-listing interpreters: allow-list concrete application
  binaries rather than interpreters/loaders.

[#_learning-cap-100-allowed-executables-per-proposal]
== Learning cap: 100 allowed executables per proposal

During *learning*, {rte-short-name} writes observed executable paths into a
`WorkloadPolicyProposal` under `spec.rulesByContainer[*].executables.allowed`.

To bound proposal growth, the learning controller stops adding new entries once
the proposal contains *100* distinct allowed executables *in total* (summed
across all containers in `rulesByContainer`). This is a design decision.

* *Impact*: if a workload executes more than *100* distinct executables, the
  proposal becomes “full” and additional executables won't be learned
  automatically. In that case you may need to curate and trim the list or manage
  policy contents manually.

[#_in-some-scenarios-the-full-workload-name-is-not-extracted]
== In some scenarios the full workload name is not extracted

With NRI, {rte-short-name} derives the workload name from the pod name format
and a small set of well-known labels. In some scenarios this information isn't
sufficient to reconstruct the original controller name.

This happens when Kubernetes truncates pod names due to the 63-character
limit (common with long `Deployment`/`DaemonSet` names), which can remove parts
of the name and/or separators that would otherwise allow reliable parsing.

In these cases, {rte-short-name} may only be able to report a shortened,
best-effort workload name and won't be able to extract the full workload name.

* *Impact*: workload names shown in policy proposals and violation reporting can
  be incomplete and may not exactly match the original Kubernetes resource name.
  Since workload type and name name is also used to derive the
  `WorkloadPolicyProposal` resource name, the proposal may be created under an
  unexpected name, which can make it look like learning didn't happen.

[#_static-pods-api-server-pod-uid-can-t-be-resolved-via-nri]
== Static pods: API-server Pod UID can't be resolved via NRI

For Kubernetes
link:https://kubernetes.io/docs/tasks/configure-pod-container/static-pod/[static
pods], the Pod UID used by the kubelet and the Pod UID assigned by the
Kubernetes API server can differ.

In the NRI context, {rte-short-name} can't reliably retrieve the *API-server*
Pod UID for static pods, and instead relies on the UID available via NRI.

* *Impact*: when correlating {rte-short-name} events/policies with Kubernetes
  objects, the Pod UID may not match what you see on the Pod object returned by
  the Kubernetes API for static pods.

[#_nri-may-not-be-enabled-by-default-for-containerd-prior-to-v2-0]
== NRI may not be enabled by default for containerd prior to v2.0

{rte-short-name} requires NRI to be enabled in the container runtime. On
containerd versions prior to v2.0, NRI may be available but not enabled by
default, depending on how containerd is packaged/configured in your
distribution.

* *Impact*: if NRI isn't enabled, {rte-short-name} won't be able to learn and
  resolve container identity correctly and may fail to operate as expected. You
  have to enable NRI manually.

[#_replicaset-isn-t-supported-as-a-workload-for-learning]
== ReplicaSet isn't supported as a workload for learning

{rte-short-name} doesn't currently learn policies with `ReplicaSet` as the
workload identity.

In the NRI context, {rte-short-name} derives the “workload kind/name” primarily
from the pod name and a small set of well-known labels. This works for common
workload types (for example, `Deployment`, `DaemonSet`), but it isn't sufficient to
reliably identify a pod as belonging to a `ReplicaSet` in the general case.

As a result, pods created by standalone `ReplicaSet` may be treated as plain
`Pod` workloads for learning and reporting purposes.

* *Impact*: policy proposals and violation reporting may not group/label these
  pods under a `ReplicaSet` workload, and may not match the workload identity
  you expect. Please use other workload types (for example, `Deployment`,
  `DaemonSet`) when you want reliable workload attribution and policy learning.

[#_arm64-kernels-prior-to-6-4-are-not-supported]
== arm64: kernels prior to 6.4 are not supported

On arm64/aarch64, {rte-short-name} requires a Linux kernel version *>= 6.4*.

* *Impact*: on older arm64 kernels, {rte-short-name} may fail to load eBPF
  programs or may not function correctly.

[#_cri-dockerd-is-not-supported]
== cri-dockerd is not supported

{rte-short-name} doesn't support running Kubernetes with Docker via
`cri-dockerd`, and there are no plans to add support.

{rte-short-name} relies on container-runtime integration that provides
consistent container/pod identity information (NRI). `cri-dockerd` doesn't meet
this requirement, so container attribution and policy enforcement behavior isn't
reliable in that environment.

* *Impact*: {rte-short-name} may fail to start correctly, or may be unable to
  reliably attribute processes to containers/workloads. Please use a supported
  container runtime (`containerd` or `CRI-O`) instead.
